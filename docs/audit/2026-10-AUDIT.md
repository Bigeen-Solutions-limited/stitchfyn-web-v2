# StitchFYN web audit, October 2026

This audit of the web app uses the same eight passes as `stitchfyn-api/docs/audit/2026-10-AUDIT.md`. It was run against `main` at `235f052`, with one PR per pass. Critical and High findings are fixed in that pass's PR, with a test. Medium and Low findings are recorded here and scheduled. Owner: Yusuf, unless reassigned.

How to read the tables:

- **Severity** follows the API audit. Critical means a security hole, money, or data loss. High means a silent failure, or production access held by AI. Medium covers duplication and missing tests. Low covers docs and cleanup.
- **Rule** is the rule number from the API audit that the pass checks.
- **Result**: ✅ means the check passed, ❌ means it failed, and "❌ → fixed" means it failed and this audit fixed it. "Owner action" means only the owner can do it, usually in an outside service's settings.
- Finding IDs (W1-1 and so on) are the web's. IDs like P1-9 point to the API audit.

## Pass 1: Inputs and trust boundaries (Rule 4)

The web app takes input from four places: what users type, URL parameters, API responses, and its own browser storage (the IndexedDB offline queue and the device id in `localStorage`). The API is what enforces the rules. This pass checks two things. The web must never turn untrusted data into code or page markup. And it must never keep credentials where a script could read them.

### Checklist

| Item | Result | Evidence |
| --- | --- | --- |
| No `dangerouslySetInnerHTML`, `innerHTML`, `eval`, `new Function`, `document.write` | ✅ | `grep -rnE "dangerouslySetInnerHTML\|innerHTML\|eval\(\|new Function\|document\.write" src` finds nothing outside tests. Every value from the server is shown as plain React text, never as markup. |
| Links built from data can't run script | ✅ | Only one `href` is built from API data: the audit metadata link (`features/audit/auditPresentation.ts`). It accepts only `^https?://`. WhatsApp and SMS share links use `encodeURIComponent`. `window.open` calls use fixed schemes or `groupShareUrl`, with `noopener`. |
| `<img src>` from data | ✅ | Image sources are Cloudinary `secureUrl` values, QR-code data URLs made by the server, or base64 fabric images the API returns. An `<img>` can't run script. |
| Credentials not readable by injected script | ✅ | The access token is kept in memory only (`features/auth/hooks/useAuth.ts`). The refresh token is an httpOnly cookie set by the API, which page scripts can't read. `localStorage` holds only a random device id, which isn't a secret (`lib/device-id.ts`). |
| Secrets not hardcoded | ✅ | The only value baked in at build time is `VITE_API_URL` (`infrastructure/http/axios.client.ts`, `features/orders/seal.api.ts`). The bundle holds no keys. |
| Validation on input | ✅ (advisory) | Forms check input only to help the user. The API is the real gatekeeper, and its gaps are in the API audit (P1-8). |
| Authorization on the resource | N/A here | Hiding things by role in the UI is a convenience, not protection. The API fixes from Pass 1 (payments, customer thread, dashboard scoping) are what enforce it. The tailor dashboard needed no change: `/analytics/overview` now returns only the tailor's own orders. |
| Webhooks | N/A | — |

### Findings

| ID | File | Rule | Severity | Finding | Fix | Owner |
| --- | --- | --- | --- | --- | --- | --- |
| W1-1 | `src/features/workflow/offline/stage-update-queue.ts` | 4 | Low | When the tailor is back online, the app sends the whole offline queue in one `POST /sync/batch`. Once the API limits batch size (API P1-9), a long spell offline would build a queue too big to send, and the API would refuse it. | When that limit lands, send the queue in chunks no bigger than the API's `maxItems`. | Yusuf |

This pass found no Critical or High findings in the web app.

## Pass 3: Error masking (Rule 3)

This pass looks for places where an error is caught and then hidden, so nobody learns that something failed.

### Checklist

| Item | Result | Evidence |
| --- | --- | --- |
| No empty or swallowing catch blocks | ❌ | One error is swallowed: `flushStageUpdates().catch(() => null)` in `features/workflow/offline/useStageUpdateSync.ts` (W3-1). Every other `catch` does one of three things. It shows the user a message (`NewOrderPage.tsx`, `GroupCoordinatorDashboard.tsx`). Or it sits in a mutation that has its own `onError` toast (`features/measurements/hooks/useMeasurementMutation.ts`). Or it returns a documented "nothing there" (`dispute.api.ts`: a 404 means there is no dispute). |
| No `?? 0` / `\|\| []` hiding a failed call | ✅ | `?? 0` appears only on counts taken from a response that has already loaded (`totalActiveOrders`, `garments.length`). Payment totals are shown exactly as the API sends them. |
| Retry limits | ✅ | React Query retries a query at most 3 times, and never on 401 or 404 (`query/queryClient.ts`). Mutations aren't retried. |
| Tests assert behaviour | ✅ | Every test file has assertions. Spot checks: `stage-update-queue.test.ts` checks the request body, which updates were synced, and that the queue is empty afterwards. `OrderMessageThread.test.tsx` checks the messages shown and the sender names. Neither stops at "the page rendered". |

### Findings

## Pass 5: Duplication (Rule 2)

This pass looks for logic copied in more than one place, where a fix to one copy can miss the others.

## Pass 7: Blast radius (Rule 6)

This pass asks how much harm one bad release or one slow service can do, and how far it spreads.

### Checklist

| Item | Result | Evidence |
| --- | --- | --- |
| Feature flags | ❌ | None. Behaviour is fixed when the app is built (`VITE_API_URL`). |
| Gradual rollouts | ❌ owner action | `DEPLOY.md` assumes Vercel. Nothing in the repo releases to some users before others. |
| Timeouts on external calls | ❌ | `infrastructure/http/axios.client.ts` sets no `timeout`. A request the API never answers keeps spinning until the browser gives up. React Query retries a query up to 3 times when it fails, but not when it hangs (W7-1). |
| Slow dependency can't take the app down | ✅ (with W7-1) | The offline queue keeps stage updates when the network fails. Pages show an error when a query fails, instead of crashing. |
| AI agents have no production credentials | ✅ for this repo | `.env` is gitignored and holds only `VITE_API_URL`. The git history holds no secrets. The GitHub `main` and token issue is the same as API P7-8. |
| Production data access and backups | N/A | The web app stores no data of its own. See API P7-9. |
